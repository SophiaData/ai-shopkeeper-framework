# 开发流程（Development Flow）

> 本文件是**一次改动从领受到合并的路径导航**：每步指向拥有该细节的文档，不复制它们的内容。
> 规则本体：[AGENTS.md](../AGENTS.md)（常驻）· [CONVENTIONS.md](./CONVENTIONS.md)（写作与归属）· [M1-PLAN.md](./M1-PLAN.md)（切片与验证）
> 版本：v1.0 ｜ 建立：2026-10-12 ｜ 状态：生效

本文件只做一件事：把散在各处的流程步骤串成一条路径。任何一步的具体要求以其「家」为准——需要判断细节时打开链接，不要以本文件为最终依据。

## 路径总览

```
领任务 → 定向 → 定界 → 实现 → 本地验证 → 双轴评审 → PR → 合并 → 收口
  │        │      │      │        │           │        │      │      │
  └ §1     └ §2   └ §3   └ §4     └ §5        └ §6     └ §7   └ §8   └ §9
```

M1 阶段的任务来自 [M1-PLAN §2–§4](./M1-PLAN.md) 的切片表（A1–A5 / B1–B5 / C1–C3）；每片已带完成条件、`blocked_by` 与 write scope，不需要另立任务编号。

## 1. 领任务

从 [M1-PLAN](./M1-PLAN.md) 切片表领取一个**依赖已满足**的切片。表中三列是领取依据：

- **完成条件**：必须可执行（命令 + 期望输出）。写不出完成条件的切片不应开工。
- **blocked_by**：前置切片未完成不得开始。
- **write scope**：本次改动允许触碰的路径。多 Agent 并行时各成员范围必须不相交。

## 2. 定向（读权威）

按 [AGENTS.md](../AGENTS.md) 的权威表，读本次改动涉及的权威文档：

| 改动类型 | 先读 |
|---|---|
| 设计 / 架构 / 模块职责 | [DESIGN.md](./DESIGN.md) |
| 数据模型 / 状态机 / DDL | [SCHEMA.md](./SCHEMA.md) |
| 切片范围 / 完成条件 | [M1-PLAN.md](./M1-PLAN.md) |
| 外部依赖行为 / 降级 | `docs/spike/*.md` 对应裁决 |

发现文档与实现矛盾时，回到权威文档解决；不允许在代码里另立第三种说法。

## 3. 定界（动手前）

- 列出将要修改的文件，与切片的 write scope 对齐。
- 若改动影响契约、实体、状态机或 API，确认权威文档对应小节的同步方案（第 4 步的同一提交义务）。
- 遇到需要 owner 拍板的新冲突，写进 [DESIGN §12](./DESIGN.md) 或 [M1-PLAN §0.2](./M1-PLAN.md)，不擅自改冻结文档。

写代码前另读 [M1-PLAN §0.1.1](./M1-PLAN.md)——那里的 7 条是 M1-A/B 实测得出的硬约束（`max_tokens` 与 `reasoning_content` 共享预算、合规信号必须分三轨、词表必须词边界+词干、供给侧信息确定性拦截等）。它们不是建议，是踩过的坑。

## 4. 实现

- 同一次提交内完成三件事：实现、受影响文档同步、验证。改契约/实体/状态机/API 时，权威文档小节是同一提交的义务，不是「回头补」。
- 注释与文档写完整契约（行为、失败、边界、所有权），不写推理流水账。
- 外部依赖按 [DESIGN §2.1](./DESIGN.md) 的 mock 先行：先实现 `MockXxx`，真实实现逐个替换，两者走同一套契约测试。

## 5. 本地验证

跑 [scripts/ci.ps1](../scripts/ci.ps1)（六步：pytest / 双库 DDL / 密钥扫描 / `.env` 未入库 / 文档链接门 / import smoke）。无 Docker 时加 `-SkipPg`，但该次运行不满足 C1，需在报告中说明。

- 关键契约要有能「故意失败」的负向用例。
- 只改文档时，链接门与事实核对即为验证方式。
- 环境差异（缺字体、缺 Docker、无 pwsh）与真实缺陷分开报告，不混入失败计数。

## 6. 双轴评审（M1 收口必做）

实施 agent 交付固定 commit 或 diff、自测命令与输出、已知限制后，由审核 agent 在该版本上审查并把报告留在 `docs/review/`；角色、归属与报告格式见 [CONVENTIONS §3](./CONVENTIONS.md)。发现退回实施方修复，复核必须指向修复后的版本。按 [M1-PLAN §5](./M1-PLAN.md)：M1 收口时 Standards 轴与 Spec 轴由**两个独立上下文分别审，报告不许合并**。

- 判据来源必须写到节号，并写明「本轴不判什么」。
- 每条发现要有可复现的证据（命令 + 输出 + 文件行号）。
- 报告必须含 `Verified clean` 与 `Not verified` 两节；没验的逐条写**为什么没验**。
- Blocker 未清不放行。

## 7. PR

**所有改动经 PR 合并，不直接推 master。**

1. 从最新 `master` 开分支，命名 `<type>/<topic>`（`feat/` / `fix/` / `docs/` / `chore/`）。
2. 提交信息说明**改了什么、为什么、怎么验证**；实测数字带来源，未验证的明确标注为推断或未能验证。
3. PR 描述按 [CONVENTIONS §3](./CONVENTIONS.md) 的标准写：背景、改动、验证结果、以及**已知未覆盖的部分**。
4. 一个 PR 只做一件事；纯机械改动（错别字、格式）可与主改动同 PR，但要在描述里点明。

### 7.1 提交粒度

**默认压缩为单个 commit**：`master` 保持线性，一个 PR 一个 commit。合并时用 squash，不产生 merge commit。

出现以下任一情况时，拆成多个 commit（PR 内保留拆分，合并时用 merge 保留各 commit）：

- 改动跨多个模块（如同时动 `src/shopkeeper/adapters/` 与 `src/shopkeeper/security/`）。
- 含契约变更：实体、状态机、API、DDL 的改动，与它们的实现分开提交。
- 一个 PR 内存在可独立验证的阶段（如「先落契约 → 再落实现 → 再补测试」）。

拆分时每个 commit 必须独立可读且不破坏构建：不允许出现「前一个 commit 编译不过、后一个才修好」的中间态。commit 信息写清该步做了什么，不写「继续上一步」。

### 7.2 合并方式

| 情形 | 方式 | master 上的结果 |
|---|---|---|
| 单 commit（默认） | squash merge | 线性，无 merge commit |
| 多 commit（7.1 的拆分） | merge commit | 保留拆分历史 |

## 8. 合并与收口

- 按 [§7.2](#72-合并方式) 选择合并方式：单 commit 用 squash，多 commit 用 merge commit。
- 合并前确认 PR `MERGEABLE` 且工作区干净；核对最终 diff 只包含预期改动。
- **Lead 自己跑一遍验收命令并核对最终 diff**，不转述评审结论（[M1-PLAN §5](./M1-PLAN.md)）。
- 合并后在 `master` 上复跑一次验证，确认合并结果仍通过。
- 切片完成后在 [M1-PLAN](./M1-PLAN.md) 对应处登记结论：贴出命令与输出，**贴不出输出视为未完成**。

## 9. 例外

**PR 流程没有例外。** 紧急修复同样开分支、走 PR、合并到 `master`——不允许直接提交或强推 `master`。

紧急修复允许压缩的是**查验步骤**，不是 PR 本身：

- 可省略第 6 步双轴评审，改为在 PR 描述中说明故障现象、影响面与「为何来不及双轴评审」。
- 第 5 步本地验证仍需执行并在 PR 中贴出结果；确实无法执行的（如依赖线上环境），写明无法执行的原因与替代观察点。
- 其余步骤（第 7 步 PR、第 8 步合并与收口）照走；合并方式按 [§7.2](#72-合并方式)。

**纯机械改动**（错别字、注释、等价重构）：可省略第 6 步双轴评审，其余步骤照走。

除上述两种，跳过任何步骤都需在 PR 描述中写明理由并经 owner 确认。
