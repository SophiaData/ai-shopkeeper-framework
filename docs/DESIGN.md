## 2. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│  控制台 Web (Next.js)                                    │
│  舰队状态 / 任务流日志 / 商品库 / 审批收件箱 / 利润看板      │
└──────────────▲──────────────────────────────────────────┘
               │ REST + SSE（任务流实时日志）
┌──────────────┴──────────────────────────────────────────┐
│  网关 API (FastAPI)                                      │
│  鉴权 / 审批闸门 / 编排器(Orchestrator)                    │
└──────┬───────────────┬───────────────┬──────────────────┘
       │               │               │
┌──────┴─────┐  ┌──────┴─────┐  ┌──────┴─────────────┐
│ 六个 Agent  │  │ 任务队列     │  │ 数据层              │
│ (无状态)    │  │ (Redis/arq) │  │ SQLite→PostgreSQL   │
└──────┬─────┘  └────────────┘  └────────────────────┘
       │ 调用工具层（每个工具=接口化的适配器，mock/真实可切换）
┌──────┴───────────────────────────────────────────────────┐
│ 工具层 Adapters：                                         │
│ 1688(采集/API)  TikTok Shop(API/RPA)  LLM  图像  物流  飞书 │
└──────────────────────────────────────────────────────────┘
```

### 2.1 核心设计原则（评审重点）

1. **闸门前置**：所有涉钱/涉店铺写操作（上架、改价、下单、投放）一律生成 `approvals` 记录，人工确认后才执行。纯读和纯生成（选品报告、listing 草稿）不过闸门。
2. **Agent 无状态**：Agent 只是「输入→工具调用→产出」的函数，状态全部落在任务和实体表上。任何一次 agent 运行可审计；原始响应分层存储（`tool_call_blobs`，加密+保留期），重放从 blob 读取（这对开源框架的信任感至关重要）。
3. **平台适配器接口化**：`PlatformAdapter` 是抽象接口（搜索商品、创建 listing、查订单、回传物流）。TikTok 实现可以有 API 版和 RPA 版，两者对编排器透明。**这是框架腿的边界，从第一天就按接口写。**
4. **外部依赖全部 mock 先行**：每个适配器先实现 `MockXxx`（确定性行为 + 固定延时），开发期全链路可跑通；真实实现逐个替换。测试入口统一为「适配器契约测试 + 编排器假 agent 测试」。
5. **店铺操作通道与主系统分离部署**：TikTok/平台访问需要海外 IP。架构上把「平台操作网关」设计为可独立部署的进程（主系统在国内开发机跑，网关部署在海外云机），两者通过带 token 的 HTTPS 队列通信——复用飞书→DSH 项目的"长轮询不暴露端口"模式。**最小可用（v1.17）**：`src/shopkeeper/gateway/`——`GatewayClient`（主系统）/ `GatewayServer`（海外 worker）/ 可选 `hub`（主系统侧托管队列，海外主动 `claim`）。`GATEWAY_MODE=local` 同进程直连适配器；`remote` 走队列。mock 用 `MemoryJobQueue` 回环，不要求真海外 IP。发货/退款在网关层硬拒。

### 2.2 责任边界

| 层 | 负责 | 不负责 |
|----|------|--------|
| 控制台 | 展示、审批交互、人工录入 | 业务逻辑 |
| 网关/编排器 | 任务编排、闸门裁决、重试策略（统一 `shopkeeper.retry`：指数退避+抖动；写副作用另走幂等审计） | 具体平台细节 |
| Agent | 生成内容、做出建议、调工具 | 直接写平台（必须经闸门放行的工具调用） |
| 适配器 | 平台协议/反爬细节、格式转换 | 业务决策 |

## 3. 模块设计：六个 AI 员工 + 三个公共模块

### 3.1 公共模块

**编排器（Orchestrator）**：任务 DAG 调度、失败重试（指数退避）、超时熔断。每个任务是一条 `task` 记录，含输入快照、工具调用日志、产出。**v1.23 最小可用**：`src/shopkeeper/orchestrator/` 声明式流程（`PIPELINE_V1`）把选品→定价→文案/图→QA→短视频脚本→达人建联草稿→八态审批→上架→订单→代发→物流→客服串成可持久化 run；状态落工作台 SQLite（`orch_*`，migrate v3）；审批节点挂起，批准/打回后续跑或回退重写；AI 步预算见 `LLM_DAILY_BUDGET_USD`；`ORCHESTRATOR_AUTORUN` 默认关。业务库 `tasks` 仍由 Scout/Stylist 管线写入；编排器不绕过闸门。**v1.37 端到端 mock 演示**：`make demo-orch` / `python -m shopkeeper.cli demo-orch` 一键串通全链路（强制 mock、不外呼）；审批经内部 `approve`（八态闸门）；产物见 `artifacts/demo-orch/`。**v1.45**：`/admin` 总览与「AI 工作流」提供「一键 mock 演示」（`POST /api/admin/demo-orch`），写入服务正在读的工作台库并深链到 run 时间线。**v1.47 短视频脚本步**：QA 通过后、审批前执行 `script`。输入是 listing 标题/卖点、时长（缺省 30 秒，合法范围 15–60）和是否挂车（缺省挂车）。默认确定性模板复述已有卖点，结构对齐 [prompts/short-video-script.md](../prompts/short-video-script.md)（分镜、3 个 Hook、封面 2 版、提词、拍摄检查）；`ORCHESTRATOR_LLM` / `LLM_CHANNEL` 非 mock 时走现有编排器 LLM。卖家原文未出现的防水、食品级、承重数字或「全网最低」以 `ORCH_SCRIPT_UNGROUNDED` 失败，不建审批。该步是纯生成，不新增员工，也不新增审批类型。`/admin/workflows` 时间线用中文标签「短视频脚本」。**v1.48 达人建联草稿步**：脚本成功后、审批前执行 `outreach`。输入是 listing 标题/卖点；达人缺省为测评、生活、出租屋改造各一条，昵称「达人」。提示词文件 [prompts/influencer-outreach.md](../prompts/influencer-outreach.md) 在时作为系统提示，缺失时用同结构内置模板；`ORCHESTRATOR_LLM` / `LLM_CHANNEL` 非 mock 时走现有编排器 LLM。草稿写入工作台 `drafts`（`kind=influencer_outreach`，待审），`make demo-orch` 另写 `outreach.json`。未在输入出现的佣金比例、粉丝数、保底播放、赠品、免打孔、已发送或规格以 `ORCH_OUTREACH_UNGROUNDED` 失败；合规词 block、供给侧泄漏或泰语质检失败以 `ORCH_OUTREACH_COMPLIANCE` 失败。失败不入库待审。`/admin/outreach` 可标记通过或拒绝，只改状态；`POST /api/workflow/outreach/drafts/{id}/send` 固定 403。不发送、不寄样、不付款、不外呼。该步不新增员工，也不新增八态审批类型。时间线中文标签「达人建联」。**v1.49**：`/admin/runs` 只读投影同一批 `orch_*` 行（状态、商品、开始时间、耗时、停步、逐步摘要、LLM 用量、错误数据，含达人建联步）；待审链到审批队列。一键 mock 演示成功后的 `href` 指向 `/admin/runs?run=<id>`。不加表。

#### 3.1.1 编排器演进对照（LangGraph / CrewAI）

是否用 LangGraph（或 CrewAI）替换自研编排器的评估与迁移建议，唯一详述在 [ORCHESTRATOR-LANGGRAPH.md](./ORCHESTRATOR-LANGGRAPH.md)。**口径摘要**：短期保留自研；中期仅在有强理由时局部引入；不建议全量替换；默认不新增编排运行时依赖。原则（闸门前置、mock 先行、涉钱不过闸门不外呼）不变。

**售价公式（Pricing，v1.24）**：`src/shopkeeper/pricing/` 纯函数。输入 `cost_cny`（CNY 分）、`shipping_cny`、`fx_rate`（CNY→THB）、`commission_pct` / `payment_fee_pct` / `ads_pct` / `target_margin_pct`、`min_price_thb`（THB satang）；输出 `suggested_price_thb`、`breakdown`、`fx_source`。费率与固定汇率占位全部来自 `PRICING_*` / `FX_CNY_THB`（非实时汇率 API）。编排器定价步：公式价优先；LLM 只产理由与可选覆盖价；偏离超 `PRICING_DEVIATION_PCT` → 挂起 `pricing_override` 审批；缺成本明确报错，不默默填假成本。预览：`POST /api/workflow/pricing/quote`。报价同时给出保本 ROAS（建议售价 / 贡献）与最高可承受 CPA。贡献 = 售价 − 佣金 − 支付费 − 到岸成本（不含广告、不含目标毛利）；最高 CPA = 贡献（一单一次转化）。传入 `actual_roas` 或 `actual_cpa_minor` 且低于保本时，`breakdown.ad_guard.ad_alert` 只提醒（`action=alert_only`），不改建议价、不建审批、不调预算。

**审批闸门（Approval Gate）**：规则落库 `gate_policies`（版本化、生效区间），每次裁决写 `gate_decisions` 留痕。执行器**原子消费**审批单（先 UPDATE 占位、rowcount=1 才外呼），外呼前 **pre-flight 复校验**（重拉现价/库存/汇率，超阈值 → `stale` 重审），并回写执行回执。闸门裁决是纯函数，输入来自规则表，独立单测。

**飞书通知器**：复用现有 飞书→DSH 项目代码（Relay+Bride 改造为库），推送审批卡片与日报。

### 3.3 每个员工的失败策略

生成类失败（LLM/图像/可重试传输）：统一走 `shopkeeper.retry.call_with_retry`（指数退避 + 抖动，`RETRY_MAX_RETRIES` 默认 2）后降级为「人工待办」；耗尽可标 `EXT_RETRY_EXHAUSTED`。**LLM 主备（v1.29）**：超时/5xx/限流先按 `LLM_FALLBACK_MODEL` 等切备用模型；全部失败回落本地模板并标 `degraded`（见错误码 `LLM_FALLBACK_EXHAUSTED`），备用调用计入 `LLM_DAILY_BUDGET_USD`。执行类失败（上架/下单）：立即停、保留现场快照、进人工待办，**不**经重试层自动重试（避免重复下单）；同键重入靠 `side_effect` 幂等回放。

## 4. 数据模型（核心表）

> **权威表清单（43 张）与全部 DDL、状态机、幂等/对账/并发设计见 [SCHEMA.md](./SCHEMA.md)（v0.7，DDL 已在 PG15 空库实测建库通过，见 SCHEMA §8）。** 此处只列业务域：

```
基础域      users / shops / shop_credentials / payout_accounts / tasks / tool_call_blobs / platform_events
目录域      suppliers / products / supplier_offers / listings / listing_versions / listing_items / inventory_snapshots / stock_sync_state
订单域      orders / order_items / order_addresses / order_status_history / shipments / shipment_items / shipment_events / disputes / order_refunds / order_refund_items / penalties
履约结算域  purchase_orders / purchase_order_items / po_status_history / platform_settlements / settlement_lines / recon_diffs
执行审批域  gate_policies / gate_decisions / approvals / external_writes / tool_calls / conversations / messages / fx_rates / ledger_entries / platform_fees / kpi_daily
```

**审批状态机（权威=SCHEMA §3.4）**：`pending → approved → executing → executed | execute_failed`，旁路 `rejected / expired / stale`。执行器**原子占位**（UPDATE 抢位 rowcount=1 才允许外呼）→ pre-flight 复校验（现价/库存/汇率超 `gate_policies` 阈值 → `stale` 重审）→ 外呼 → 回写执行回执；`executing` 由 reaper 兜底防悬空。载荷哈希防篡改；`entity_id` 与载荷内业务 id 强一致。

## 7. 合规硬规则（写进代码，不是文档承诺）

1. 履约只允许 `supplier_offer.warehouse_type ∈ {overseas_warehouse}` 且时效承诺 ≥ 平台要求 + 缓冲天数。
2. 物流单号必须真实可查（承运方 API 校验），SLA 超时订单自动触发客服话术 + 供应商拉黑计数。**P2-03**：回填前必须过承运商白名单与单号格式（Thailand Post 另核 UPU S10 校验位）。`TRACKING_LOOKUP_ENABLED` 默认关，此时不外呼，`lookup_confirmed=false`，格式通过不等于承运方已确认。打开后只发一次只读 GET；未找到、身份不一致、超时或响应不可用则不回传。`update_tracking` 真写仍受 `TTS_WRITE_*`，默认关。SLA 自动话术与供应商拉黑仍后置。
3. AI 生成内容（图/文）按平台要求打标；图上不保留 1688 水印（重绘流程内嵌检查）。**M2 边界（承接 M1）**：Pillow 后处理仍为主链路；真重绘经 `ImageRedrawAdapter`，默认 `IMAGE_REDRAW_ENABLED=0`。水印检测器仍只覆盖右下角红橙角标——检不出即放行并写 warnings，**不计入** `needs_human`（标记恒真等于没有标记）；全图 OCR 复检仍后置。见 [spike/image.md](./spike/image.md)。
4. 合规词黑名单随站点配置（美区/东南亚词表不同），listing 生成与上架前双重校验。**实现**：词表文件 `src/shopkeeper/assets/compliance_lexicon.json`（`shopkeeper.compliance` 加载）；条目含 `severity=block|warn` 与类目（医疗/绝对化/品牌/价格欺诈/站点限制等）；`block` 命中返回词与位置，文案不可进入审批通过；`warn` 仅提示。词表为公开常识类示例，**非法律意见**，须店铺 owner 对照平台最新政策人工复核。`SEA` 站点别名映射 `TH`（§12.1）。
5. 上述规则违反时闸门直接拒绝，不提供"本次跳过"选项。
6. 一切 JSONB/长文本列落库前过统一脱敏守卫（按数据类型判定，SCHEMA §4.4）：PII 只能以 `pii_ref` / HMAC / 加密 blob 形式存在。**输出路径（v1.33）**：结构化日志与告警外呼前再跑片段脱敏（`security/log_redaction.py`），避免买家姓名/电话/地址/聊天内容进 stderr 或 webhook。**保留期（v1.33，v1.91 默认演练）**：工作台对 `synced_orders` / `cs_*` 及过期 JSON 列按 `PII_RETENTION_DAYS`（默认 90）覆写过期 PII（`workflow/pii_retention.py`，migrate v5 + `pii_purge_audit`）；财务字段（订单号、金额、状态等）保留。`PII_PURGE_DRY_RUN` 未设置时只写审计、不改库；真覆写须显式设 0。`/admin` 设置页只读显示上次清理时间与计数，不提供关闭演练或触发删除的入口。备份 manifest 声明同策略；历史备份可能含清理前明文，须轮转。以上为工程默认，**非法律意见**，不构成泰国 PDPA 合规保证。
7. 平台侧库存 = min(供应商库存 × buffer_ratio, 每日上限)；供应商断货或报价失效 → 熔断 `cutoff` → 触发下架审批（SCHEMA §3.1）。
8. 平台凭据已知失效时，闸门硬拒出站写（SCHEMA §3.0 的 `auth_state != valid` 口径；工作台未落 `shop_credentials` 表，判定在 TikTok 客户端）。`TIKTOK_ACCESS_TOKEN_EXPIRE_AT` 已过当前时间，或产物文件记下一次已映射的授权失败（HTTP 401，或 105002 / `TTS_AUTH_EXPIRED`）时，`create_product`、`upload_image`、`update_stock` 返回 `TT_AUTH_INVALID`，不发这些请求。72h/24h 临期只告警，不冻结；未设到期时间不视为已失效。只读请求仍按原客户端发出。令牌刷新成功，或到期时间更新到更晚的未来时间，解除冻结；写通道仍须 `TTS_WRITE_*`，本规则不打开它。标记文件只含时间与错误码，不含密钥。

## 11. 风险登记册

| 风险 | 等级 | 缓解 |
|------|------|------|
| 无货源代发被平台判定违规（假单/时效） | 高 | §7 硬规则；只接海外仓；首月小量慢跑 |
| TikTok 政策变动（AI 内容/数字人/跨境准入） | 高 | 入驻时人工核对最新规则；架构上平台规则集中在一个适配器内 |
| RPA 被风控 | 中 | API 优先；RPA 只兜底；操作节奏限速+随机化 |
| 虚拟库存超卖（供应商断货） | 高 | `stock_sync_state` 缓冲系数 + 断货熔断自动下架（SCHEMA §3.1） |
| 平台凭据失效（token 过期/撤销授权） | 中 | 到期 72h/24h 告警；已知失效（本地到期时间已过，或观察到 HTTP 401 / 105002）时闸门冻结出站写（v1.99，`TT_AUTH_INVALID`）。工作台未落 `shop_credentials` 表 |
| 汇率/费用算错导致利润失真 | 中 | 台账两跳汇率 `fx_legs`（SCHEMA §5）+ R1-R3 冲正规则（§4.3）+ 结算单对账（§4.7） |
| LLM 幻觉写进商品文案 | 中 | 合规词过滤 + 上架前人工审（闸门兜底） |

> - v1.76（2026-10-16）：`insert_ledger_entry` 的幂等改由数据库保证（独立复核发现）。原实现是「先 `get_ledger_entry_by_key()` 查、再 INSERT」，而文档承诺「冲突时跳过（幂等）」—— 两个并发调用会**都**查到「不存在」然后**都**去插，后到的撞 UNIQUE 约束抛 `IntegrityError`。**实测 20 线程同键：1 个成功、19 个抛异常。** 台账是只追加账本，异常逃出去会让调用方（对账/回填）整批失败；更糟的是调用方若「捕获后重试」，会在不知情的情况下**重复入账**。现改为 `INSERT ... ON CONFLICT(entry_key) DO NOTHING`（本文件其它写原语早已是这个写法），让数据库做原子判定，冲突时再读回已有行。修复后 20/20 成功且库里恰好 1 行。**顺带实测确认另外三个 claim 原语是真正原子的**（20 线程竞争各自恰好一个赢家）：`claim_job`（每日去重）、`claim_external_write`（防重复上架的最后一道闸）、`transition_approval`（审批闸门的原子消费点，`rowcount != 1` → None 的 CAS 确实生效）。
> - v1.76（2026-10-16）：飞书共享密钥改用常量时间比较（独立复核发现 S2）。`feishu.py` 的 verification token 与 challenge token 两处都用 `!=` 比对，而**同一文件里的 HMAC 签名分支已经用了 `hmac.compare_digest`** —— 同一类共享密钥、两种写法。时序攻击在网络路径上可利用性不高，但两种写法并存本身就是隐患：后来的人会照抄更简单的那种。现两处均改为 `hmac.compare_digest`，**校验语义不变**（错的仍拒、对的仍放行，有正反用例守着）。

> - v1.76（2026-10-16）：**业务日按曼谷时区归属**（独立复核发现，已复现）。`profit._coerce_date` 对带偏移的字符串直接 `.date()`，等于**丢掉偏移** —— 同一时刻会因为写法不同落到不同的业务日：`2026-10-08T17:30:00Z` → 10-08，而 `2026-10-09T00:30:00+07:00` → 10-09（两者是同一时刻，真实曼谷业务日为 10-09）。**而 TikTok 返回的是 UTC 时间戳**，所以实际数据走的正是错的那条路 —— 17:00–24:00 UTC 支付的单子被算进前一天，按天/按周的 P&L 与 ROAS 错位（广告费甚至会落到完全没有销售的那一天）。现新增 `_local_date()`：aware 时间一律 `.astimezone(BUSINESS_TZ).date()`，epoch 秒/毫秒同样换算；`BUSINESS_TZ` 与 `workflow/jobs.py` 的 `BANGKOK` 同源（DESIGN「定时任务时区 Asia/Bangkok」）。**边界**：naive 时间**不挪动** —— 数据源没给时区时当成 UTC 会凭空挪一天，更糟。
