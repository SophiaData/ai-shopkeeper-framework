# 文档与评审规范（Documentation & Review Conventions）

> 适用范围：本仓库全部文档与评审报告的写法、归属与验证方式。
> 上游权威：[DESIGN.md](./DESIGN.md)（产品设计唯一权威）· [SCHEMA.md](./SCHEMA.md)（数据边界唯一权威）
> 本文件只写**写法与归属规则**，不复制 DESIGN/SCHEMA 正文，不复述 M1-PLAN 的切片内容。
> 版本：v1.0 ｜ 建立：2026-10-12 ｜ 状态：生效

本仓库已有 `DESIGN.md` §2.1 五条设计原则、`M1-PLAN.md` 切片纪律、`SCHEMA.md` §2.1「矩阵即法律」，以及 `docs/REVIEW-cc*.md` 七轮设计评审加一轮冻结终审与两份 axis 报告。它们合起来已经形成一套可用的做法，但做法本身没有被写下来：新会话只能靠模仿既有文件才知道该怎么做，评审报告的质量依赖写作者自觉。

本文把那套既有做法固化成文。规则若与既有文档冲突，以既有权威文档为准并在本文修正；本文不新增与它们竞争的口径。

## 1. 文档归属：一个事实只有一个家

一份文档只详述自己的主题；对下层只描述目的、职责与高层行为，细节链接到拥有它的文件。判断归属时问「这个事实由谁维护最不容易腐烂」，而不是「放哪里最顺手」。

| 事实类型 | 家 | 不住在 |
|---|---|---|
| 产品目标、架构、模块职责、里程碑 Done 条件 | [DESIGN.md](./DESIGN.md) | 文档里复述一遍；实现细节 |
| 数据模型、状态机矩阵、守恒式、DDL | [SCHEMA.md](./SCHEMA.md) | 代码注释里另立口径 |
| 切片拆分、完成条件、write scope、blocked_by | [M1-PLAN.md](./M1-PLAN.md) | 会话记录、任务看板的复述 |
| 本轮为什么这么选、放弃了什么 | 评审报告 / `docs/spike/*.md` | 正文（正文只写现状） |
| 外部依赖裁决（通/不通 + 降级） | `docs/spike/*.md` | 散落在各处的一句话结论 |
| 真 API 只读集成如何跑、所需 env 占位 | [REAL-TESTS.md](./REAL-TESTS.md) | 在 DESIGN/README 复述命令与变量表 |
| 写法与归属规则 | 本文 | 各文档各自的「写作要求」小节 |

发现同一规则出现在两处时，保留拥有它的那个文件，另一处替换为一行链接。`DESIGN`/`SCHEMA`/`M1-PLAN` 三者边界由本表确定；本文自身不承载产品事实。

## 2. 写作规则

1. **只陈述现状。** 历史与过程写进 commit、评审报告或 spike 文档。正文写"现在是什么"，不写"原来是什么""本次修改了什么"。需要引用历史时链接到拥有它的层级。
2. **一段一个物理行。** 段落不硬换行，用编辑器软折叠。`DESIGN.md`/`SCHEMA.md`/`M1-PLAN.md` 均如此，diff 与机械检查按行对齐。表格、列表、代码块除外。
3. **写完整契约，不写推理过程。** 要覆盖行为、失败方式、时序、所有权、异常与后果。删除实现流水账、测试走读、对代码的复述。
4. **直接写，点名道姓。** 写出确切的对象名、命令、类型、字段、节号。不用比喻指代具体机制。
5. **克制使用强调。** 加粗只留给真正改变行为的那个分句。通篇加粗等于没有加粗。
6. **示例与命令必须为真。** 文档里的命令要实际可跑，引用的文件与锚点要存在。实测数字标明来源与时间；做不到实测的明确标注为推断。
7. **事实带来源。** 外部事实（供应商能力、额度、条款）给链接；本仓库事实给文件路径与行号或节号。「我是这么理解的」不算来源。
8. **不编造、不冒充。** 未接通的能力只写「计划 + 当前限制」，不写成已有行为。这一条与 `DESIGN.md` §7 的"写进代码，不是文档承诺"同源：文档承诺与代码行为必须一致，不一致时以代码为准并立即修文档。

## 3. 评审报告的既定结构

`docs/review/standards-axis.md` 与 `spec-axis.md` 确立了本仓库评审报告的结构。正式审核报告统一落在 `docs/review/`，以审查对象和日期命名（例如 `order-workbench-spec-axis-20261020.md`）；实施方案和验收记录仍由各自权威文档维护，审核报告只记录固定版本的发现与证据。新报告沿用下表，不另立格式。

| 小节 | 内容 | 硬性要求 |
|---|---|---|
| 抬头 | 审查对象、判据来源（唯一权威）、被审文档、执行时间 | 判据来源要写到节号；写明"本轴不判什么" |
| Blocker / Major / Minor | 按严重度分组，每条：要求原文 → 主张 → 实际 → 证据（命令与输出）→ 判据 | 每条必须可复现；给文件路径与行号 |
| Verified clean | 主动核验并通过的项，附核验方法 | 区分"我跑了"与"我读了" |
| Not verified | 没验的项，逐条写为什么没验 | 不得留空，也不得用"未发现异常"代替 |
| 总判 | 一句话结论 | 与上面各节的严重度一致 |

评审纪律（M1 双轴要求出自 [M1-PLAN.md](./M1-PLAN.md) §5）：

- **实施与审核分离。** 实施 agent 依据任务的 write scope 修改代码、测试和受影响的权威文档，运行自测并交付固定 commit 或 diff、命令与输出、已知限制；审核 agent 对该固定版本只读审查，不替实施 agent 修代码，也不把实施方的测试陈述当作自己已验证。修复发现后，实施方交回新版本，审核方只复核受影响项并注明版本变化。
- **双轴隔离。** M1 收口时 Standards 轴（是否符合 `DESIGN` §2.1 与 `SCHEMA` 口径）与 Spec 轴（是否忠实 M1 Done 条件）由两个独立上下文分别审，报告分别落 `docs/review/`，不合并成一个通过意见。审核者若同时承担任一轴，只能撰写自己的那一轴；另一轴交给独立上下文。
- **Lead 自己跑。** 收尾必须由 Lead 亲自跑一遍验收命令并核对最终 diff，不转述审查结论。

## 4. 验证纪律

- **没有新鲜证据不得标 completed。** 完成条件必须是「命令 + 期望输出」；贴不出输出的，视为未完成（[M1-PLAN.md](./M1-PLAN.md) §1）。
- **负向用例优先于正向覆盖。** 测试通过只证明代码跑过，不证明场景正确。关键契约要有能「故意失败」的用例：审前拦截、未通过图不得流入下游、幂等键冲突、429 冷却、unknown 不重发。
- **机械可查的不靠自觉。** 能用脚本判定的规则落地为 `scripts/` 下的门，接入 `scripts/ci.ps1`。已有的门见 `ci.ps1` 当前步骤；新增门要在本文第 1 节确认归属后再加。
- **失败要归属明确。** 测试要覆盖"供应商失败但用户得到明确说明"的路径，而不只测成功路径。
- **环境差异与真实缺陷分开写。** 本机跑不通（缺字体、缺 Docker、无 pwsh）不等于实现有缺陷；报告里必须写明根因与影响范围，不得混入失败计数。

## 5. 未决事项的记录方式

需要 owner 拍板的事项不散落在正文，集中在两个既有清单：

- `DESIGN.md` §12 未决问题——设计层面的口径待定。
- `M1-PLAN.md` §0.2 待你拍板——跑切片过程中冒出的新冲突，不擅自改冻结文档。

每条要写：冲突是什么、实测证据、建议方案、不决策的后果。决策落地后从清单移入对应权威文档，并在原处留链接。

## 6. 本文不覆盖的范围

- 不建立文档分层目录树（`docs/cookbook/`、`docs/postmortem/`、`docs/subsystems/`）。本仓库文档全部平铺在 `docs/` 及其 `review/`、`spike/` 子目录下，为这个规模预建分层目录是空转。
- 不引入 ADR 目录。`DESIGN` §12 与 `M1-PLAN` §0.2 已承担"为什么这么选"的记录职能；M2 出现并发改动、决策需要独立生命周期时再评估。
- 不定义严重度分级的技术判据（什么算 Blocker）。现有两份 axis 报告已给出可参照的尺度，写作者按同样尺度判断。
