## L1. `get_shipment_for_order` 在时间戳并列时返回任意一行

**位置**：`src/shopkeeper/workflow/store.py` `get_shipment_for_order()`

```sql
SELECT * FROM shipments
WHERE order_id = ? AND direction = 'forward'
ORDER BY created_at DESC LIMIT 1
```

**现象（已复现）**：`created_at` 只在 INSERT 时写一次，精度到微秒。
构造三条 `created_at` 完全相同的 forward 记录后，
「取最新」返回的是**中间那条**，而不是最后写入的 ——
SQLite 对并列行不保证顺序。

**为什么现在不改**：

1. **正常路径是对的**。`upsert_shipment` 的唯一键是
   `(order_id, direction, carrier, tracking_no)` —— 换单号会**新建一行**，
   时间戳几乎必然不同。实测「换单号后取最新」返回正确的后写行。
2. 只有**同微秒写入**（或时钟回拨）才会撞并列。这是个边角情形。
3. `shipments.id` 是**随机 uuid**，所以加 `id DESC` 只是把
   「不确定」变成「**确定但任意**」—— 并没有变成「取最新」。
   **加一个看起来像修复、实际没解决问题的东西，比不加更糟**：
   后来的人会以为这个坑已经填了。
4. 要真正做到「取最新」需要**新增单调列**（如自增序号），
   也就是一次 schema 变更（下一个迁移是 **v10**）。
   为边角情形引入 schema 变更，收益不成比例。

**什么条件下必须改**：

- 有真实工单出现「同一个 order 的 forward 记录时间戳并列」时；
- 或者将来因为别的原因引入 v10 时（**顺手加**单调列，那时成本近乎为零）。

**当前规避**：调用方如需精确的「最新」，用 `list_shipments(order_id)`
自行按业务规则选取，不要依赖本方法的隐含顺序。

## 记这件事的理由

同一轮复核里，其余发现我都修了（迁移半成品库、备份失败静默放行、

出站 PII / SSRF）。**这一条是唯一一个「确认有问题、但判定不该现在改」的。**

**一个被明确记录的限制，和一个没人发现的 bug，风险完全不同。**
